# Agent-assisted mapping — implementation plan only

Prepared 13 October 2026. The discovery gate, analysis worker, proposal storage and conversation feature described here are **not implemented**. The current task only simplifies the existing WordPress mapper to Static template / Dynamic template. Neither backend, the posting-agent repository, n8n nor Google Cloud is changed.

## Preferred data flow: plugin pushes snapshots, then pulls proposals

`WordPress plugin → bounded site snapshot → analysis job → stored proposal → plugin review → human approval → local creation default`

The plugin collects the endpoint schemas and selected representative posts/pages locally. It sends only the authorized snapshot to the analysis service and gets a job ID. The service infers and retains pending proposals; the plugin checks job status and retrieves them for review. The agent receives no WordPress connection, administrator credential or ability to call back into the site. **Read-only applies to the site:** storing a pending proposal and job status in the analysis service is intentional and does not activate a WordPress mapping. If evidence is insufficient, the result requests specific additional examples or answers; the plugin validates those requests against the granted endpoint/item scope before sending another bounded batch, rather than accepting arbitrary URLs from the agent.

Keep the contract independent of hosting. It can initially run as a separate isolated mapping-analysis service/job with its own proposal store, reusing the posting-agent infrastructure principles. It could later become a segregated feature inside posting-service, provided its jobs, data permissions and API scopes cannot reach posting execution. That future hosting decision does not change this plugin-side proposal/review flow and is not authorized for implementation in this task. No existing backend is required to change for the current UI work.

## Intended client experience

All supported content destinations appear in the onboarding overview. Products remain Coming soon and NOVA-owned CPTs remain Automatically mapped by NOVA; neither needs client configuration. Native taxonomies are included only when the site uses them as actual content destinations.

For each configurable endpoint, NOVA examines representative existing items and proposes one creation default. The client sees a suggested template with plain explanations, highlighted editable content, and example pages. Static means the same fields and quantities every time; Dynamic allows variable quantities and optional parts, with fixed branding or other surrounding elements retained. Existing-item rewrites still use that item's actual filled document rather than a guessed creation layout.

The review asks concrete questions: “Can FAQ items be omitted?”, “Should every section have a heading?”, “Keep this call to action on every page?”, “Do these desktop sections belong in the same mobile tab?”. Low-confidence decisions become questions, not silently activated rules. The client can choose **Looks right**, **Ask NOVA to change it**, or **Edit manually**. Conversation and manual editing change the same candidate, with an inspectable before/after preview and undo. Advanced nested/projection/layout controls remain available without dominating the default review.

Only an explicit approval activates the proposed endpoint default. A changed live source, schema or default requires renewed review. NOVA-generated suggestions stay marked **Suggested — needs review**, distinct from system-owned Automatically mapped by NOVA.

## Build sequence

1. **Collect a bounded read-only snapshot inside WordPress.** Reuse the module's local discovery/capture methods to collect supported endpoint capabilities, paginated representative item IDs, native field/container structure, ACF declared layouts/constraints, protected paths, current defaults and explicit completeness flags. Support administrator-selected examples and exclude private content unless granted for this scan. Include site/resource/reference identities, installed provider versions, complete native/schema digests and evidence references. Keep the complete native frame in trusted plugin storage and export opaque frame/pattern references plus a sanitized structural view; a blueprint seal does not hide embedded protected settings or integration secrets. Do not infer repeatability or mandatory fields from one example.

2. **Submit authenticated analysis jobs and retrieve results.** Define a hosting-neutral contract for upload, job status, proposal retrieval, cancellation and bounded conversation turns. Bind each job and result to the verified site/tenant, snapshot digest, endpoint and proposal revision. Use expiring, revocable job/result capabilities through the trusted plugin; the model sees none of those tokens. Validate upload size and structure, redact sensitive values and enforce retention/cleanup. Scope result access to its owning site, protect against replay/cross-tenant requests and verify the intended service origin. Do not expose a generic WordPress administrator connection or inbound save/draft/recovery route to the service. An agent-callable discovery gate can remain a later optional extension; it is unnecessary for this push-first flow.

3. **Analyze the supplied snapshot in isolation.** Reuse bounded asynchronous jobs, credential isolation and independent verification from the existing posting agent. Create an analysis-only worker/flow with a separate minimal service account and no trusted write executor, publishing session, posting status/URL writes or production queue input. Prefer dataset-only analysis with no outbound access to customer sites; the existing broad browser gateway is not needed. If public vendor documentation is needed, use a separately bounded credential-free reader. The model sees no administrator/CMS/n8n/cloud credentials. Site content is untrusted evidence, never permission or agent instructions. Bound runtime, tokens, requests and retained evidence; redact traces and define expiration/cleanup.

4. **Infer and store pending proposals.** Output a versioned candidate referencing the snapshot: endpoint, Static/Dynamic choice, known field bindings, allowed repeat/optional/nested regions and declared variants, instructions, required/empty behavior, decision evidence, uncertainty and client questions. Keep the native frame, styles, IDs, dynamic references and ACF definitions immutable. Translate UI Dynamic to existing compatible recipe semantics. A service-side verifier can check evidence and structural consistency, but neither agent activates a default. Store only a pending proposal, separately from any active/publishing configuration; return partial results and questions instead of guessing unsupported fields.

5. **Pull into intuitive review and compile locally.** The plugin fetches pending proposals for its own job/site, resolves opaque references against its retained snapshot, rejects unknown/protected paths and constructs the candidate with the trusted local native frame. Compile short/long/empty/nested examples through the existing deterministic recipe engine before showing a ready-to-review state. Bind every conversation patch to the snapshot, endpoint and candidate revision; return to validation after each accepted patch. Show a simple summary and required questions first, content highlights and desktop/mobile structure previews second, and manual advanced controls on demand. Actual provider styling needs a separate client-requested native review draft, unavailable to the agent service.

6. **Approve and activate through the existing trusted UI.** Validate administrator permission and nonce, final proposal digest and explicit approval. Re-read the source/provider/ACF schema and compare snapshot/default/profile revisions before saving. Record the approving actor and exact candidate; current blueprint seals and preview receipts prove consistency, not human approval or live source freshness. Make “Approve as this endpoint's creation default” explicit, retain history/rollback and never silently overwrite an active default after a scan or chat turn.

7. **Validate the boundary before rollout.** Test that the service/model has no route or credential to save, create/recover a draft, activate a module or reach a posting executor; test cross-tenant result retrieval, expired/replayed job capabilities, malicious proposal patches and outbound network denial. Include prompt injection, private-field redaction, snapshot completeness/pagination, contradictory samples, interrupted jobs, polling/retry without duplicate jobs and source changes during review. Exercise Static/Dynamic, optional empty content, nested ACF and responsive builder patterns. Start on staging with synthetic snapshots; existing defaults and pages must remain unchanged until human approval.

## Existing code to reuse and restrict

`class-nova-bridge-suite-layout-recipes.php` owns recipe catalog/design/region/preview/translate, revision/default checks and draft operations. `class-nova-bridge-suite-document-mapping.php` and `class-nova-bridge-suite-endpoint-mappings.php` expose endpoint discovery, filled documents, `targets_complete`, native source versions and `preview_read_only`. `class-nova-bridge-suite-recipe-builders.php` / `class-nova-bridge-suite-recipe-acf.php` provide provider capture and declared fields; the shared recipe engine validates/compiles a proposal. The guided editor is `assets/layout-recipes.js`.

The push-first flow reuses the underlying local catalog/design/region/preview/translate logic; it does not need to authorize external callers on those WordPress routes. A later optional pull/discovery extension would require explicit method-plus-route scoped authorization and input checks. Existing POST mapping save/creation replaces the active endpoint default; POST native draft writes a page and journal. Existing **GET draft recovery can also update the journal**. Do not treat GET as proof that a route is read-only, and do not give the model a general administrator application password.

First deliverable: local read-only snapshot export + analysis job/result contract + validated stored proposal + plugin pull/review/approval, using the existing editor and compiler. Conversation refinement can follow on the same proposal contract. Hosting within posting-service, backend mapping synchronization and publishing are separate decisions/work.
