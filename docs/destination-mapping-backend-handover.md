# Destination mapping backend handover

The WordPress plugin is now prepared for destination mapping: clients describe what each existing template field can hold and add optional rules or human instructions. Posting-service should fit NOVA's existing generated content into that description. WordPress remains responsible for native routing, writes, verification and recovery. No change to NOVA generation or nova-db is required for this scope.

Version 3.0.0 on `api-mapping-with-context` now supports preparing, saving and exporting these descriptions without a live NOVA connection. Synchronization of this new model is deliberately blocked against the reviewed stock-field API. This document describes what the backend needs to consume and return so we can connect the prepared plugin and run the first adaptation test.

## What the plugin prepares

New drafts use destination descriptions rather than a mandatory NOVA source selection. Each selected field has a stable ID, a destination label, purpose, accepted value type, optional structured limits, a required/optional choice and optional human instructions. The local editor supports `text`, `rich_text`, `url`, `email`, `image`, `list` and `link` descriptions. These describe desired values; selecting a type does not install a native writer for it.

Clients can declare fixed groups containing existing slots. Groups and slots have UUIDs; slots retain explicit ordinals and reference the selected destination field IDs. Capacity is the number of selected slots. This does not create, remove or reorder WordPress rows. Two descriptions addressing the same native field or overlapping region are rejected. Protected and Leave empty fields stay outside the content-adaptation export. Bounded instruction text preserves literal formatting and URL examples such as `<br>` and `/path%20example`; those strings are not executed or saved as native content.

Template and field instructions are available for edge cases such as “place exactly one relevant label here.” They supplement measurable limits and are not brand-voice or topic-generation settings. Existing instructions and source mappings remain available for explicit review; old approved profiles are not rewritten. Mixed historical source/repeat bindings cannot silently become a destination-only export.

## Export and example

After saving, the editor's **Export backend description** button reads the trusted server description and checks its saved revision before downloading it. The download contains `status: prepared_local`, an opaque local revision, a SHA256 of the canonical description, and the description itself. A changed layout, missing target or unresolved historical bindings yields `needs_review` instead.

The [example JSON](examples/destination-template-description.json) was generated by the plugin adapter using synthetic destinations. It is a handover format, **not a request supported by the current posting-service schema**. The backend may adopt this shape or provide an equivalent authoritative contract; we will translate at the plugin's existing adapter boundary.

| Description property | Meaning |
| --- | --- |
| `format` | Local handover format `nova-template-description/v1` |
| `name`, `page_type` | Publishing-template identity for the client |
| `instructions.mode`, `instructions.text` | Explicit inherit/set/clear choice and resolved template instructions |
| `fields[].id` | Stable destination ID; no WordPress address is needed by the adapter |
| `label`, `purpose`, `value_type` | What this destination is for and what value it can hold |
| `required`, `instructions` | Presence requirement and optional field-specific guidance |
| `constraints.max_length` | Optional scalar character limit |
| `constraints.min_items`, `max_items` | Optional list cardinality limits |
| `element`, `logical_field` | Optional discovered semantic context, such as a button's text setting |
| `groups[].id`, `label`, `capacity`, `slots` | Fixed group identity and selected existing capacity |
| `slots[].id`, `ordinal`, `field_ids` | Existing slot identity/order and the destinations belonging to it |

Native paths, post IDs, provider selectors, protected content and credentials are excluded. The local profile retains that routing information. The export digest identifies the local description; it is not a remote revision or a delivery ETag.

Local bounds are 256 KiB per draft, 500 selected fields, 64 groups, up to 500 slots per group, and 8,000 UTF-8 bytes for template or field instructions. Group members must be distinct selected scalar destinations. `max_length` is a positive integer up to 100,000; list item bounds are integers from zero to 500, with maximum no lower than minimum. Length rules apply to scalar types; item rules apply to lists.

## Backend integration required

The reviewed posting-service master `145fbcfb7319333e6369796489c068196cb68665` and develop `da51ba64aff39ca79291765081479a7b40a7ad81` expose direct stock-source mappings. Their template schema does not accept these descriptions, instructions or limits, and delivery admission copies stock content unchanged. A separate deployed adaptation implementation has not been verified. If it already exists, supply its current contract and implementation/release rather than building another layer. [Reviewed template schema](https://github.com/InSpace-GEO/posting-service/blob/145fbcfb7319333e6369796489c068196cb68665/service/openapi/posting-service.v1.yaml#L971), [delivery admission](https://github.com/InSpace-GEO/posting-service/blob/145fbcfb7319333e6369796489c068196cb68665/service/src/delivery-snapshots.ts#L60).

The necessary backend behavior is:

1. Accept, validate and retain destination definitions, supported rules and template/field instructions through the shared publishing-template API. An exact stock `source_field` binding must not be mandatory for every destination. Reuse template revisions, page settings and defaults.
2. Adapt the existing NOVA source content to the selected description inside posting-service. For example, turn source content into a short button label, one badge label and three distinct step headings/bodies. Fit content to those existing slots rather than return extra rows or copy the same source blob into every field.
3. Return the final values associated with the configured destination IDs, alongside the existing source/delivery identity and frozen configuration. Provide the exact scalar/compound value shapes in the authoritative OpenAPI. For scalar testing, the plugin already has a local validator accepting `{destination_id: value}`; the HTTP envelope still needs to be connected to the real contract.
4. Validate hard type, length, presence and capacity rules before making a delivery available. Retain the final adapted result with the selected configuration. Delivery GET and retries must return that same result rather than run the LLM again. A fitting failure must be explicit, without silently truncating values or dropping unmatched destinations.

The existing discovery, receipt, publication-event and recovery lifecycle can remain. Backend acceptance of an event and its application to NOVA are separate facts; both must be observable for the test. No WordPress-specific API or CMS credentials in posting-service are needed.

For scalar values, the prepared plugin distinguishes absence/null from an explicit empty string: absent optional values skip replacement; missing/null required values fail; an explicit empty string remains an intentional supplied value. URL and email values are validated. Local character counts use Unicode code points; rich-text length counts text after stripping tags and decoding HTML entities. Confirm equivalent backend semantics in the contract.

## Remaining plugin connection and native scope

Once the authoritative API is available, update the pinned schemas and translate the prepared description into its supported template request. Connect the fitted-value response to the retained native profile and existing writer. Synchronization and native approval must refer to the exact remote revision; old deliveries continue using their approved historical profile.

The local scalar validator is a preparation/test seam, not a remote delivery endpoint or an activated publication path. Image, list and structured-link values are deliberately rejected by this helper until a typed native adapter is verified. Existing verified writers cover scalar WordPress/ACF destinations and static Elementor heading, rich-text and button-text settings. Elementor button URLs and compound ACF link/image/list objects still require native implementation and verification before publication.

Protected preserves content on updates and clones. Leave empty skips updates and clears clones. Generic REST context remains off for these mappings; NOVA's own CPTs remain separate. Optional predefined mappings for those CPTs can be added independently.

## Validation and first real test

The preparation passed 18 offline script suites, including the existing publication/recovery checks. Final focused counts are 140 PHP draft checks, 37 description/scalar-validation checks and 29 JavaScript checks. The JavaScript checks mount the editor and exercise source-free saves, explicit legacy migration and saved-export success/conflict paths. PHP lint passed for 62 files.

Three isolated staging canaries passed against WordPress 7.1.2, PHP 8.1.34, ACF 6.8.0.1 and Elementor 4.1.4:

| Canary | Result |
| --- | --- |
| Destination drafts and export | 100 real REST/storage, permission, revision, capacity, privacy, exact instruction bytes and preservation checks |
| Existing template synchronization | 64 checks through the real client with simulated NOVA HTTP |
| Existing delivery and recovery | 151 native/journal/event checks with simulated NOVA HTTP |

The draft canary was rerun after the final literal-instruction preservation fix; the earlier synchronization and delivery passes remain separately recorded. The [test results](examples/destination-mapping-test-results.json) include the suite output, source hashes and staging evidence. The standalone preparation checks can be repeated from the plugin root:

```sh
php modules/api-mapping-context/tests/mapping-drafts-unit.php
php modules/posting-service/tests/destination-description-unit.php
node modules/api-mapping-context/tests/mapping-drafts-unit.cjs
```

The candidate was loaded only for CLI testing. Installed plugin version 2.8.12, settings and activation were preserved; temporary fixtures and candidate files were removed. The optional subscriber check was skipped because no subscriber existed. These tests do not establish real LLM fitting, a deployed API round trip or application of publication events by NOVA.

We will run the first real adaptation test ourselves once the contract and usable shared API/site credentials are available. Use one staging template with a heading, rich-text section, three fixed step slots and one badge instruction. Synchronize and approve its revision, obtain one real adapted delivery, inspect the returned field IDs and rules, write a draft, then publish and confirm backend application. Retain the resulting test post and redacted per-post requests. Replay the same delivery and a lost event acknowledgement to check that neither fitted output nor native content is written again.
